# Content freshness and scoped updates

Read when deciding what changed in an existing article. Use the current page, approved update notes, project evidence and [source verification](../../write-content/references/fact-checking.md).

## Choose the update

Check the facts that affect the reader's current choice: product availability, compatibility, process steps, official eligibility, prices or dated research used in a recommendation. Record the source and date checked. A current competitor page can reveal a missing question, but its recency alone does not establish that the existing answer is wrong.

Use page/query performance as context for prioritization. Decline or an update-date overlap supplies a reason to investigate; neither identifies a cause by itself. A high-ranking page can still contain a wrong specification; a lower-ranking page can contain an accurate explanation.

Separate what to keep, strengthen, replace or add. Choose the depth from the actual problem and user's scope. Retain useful source material, links, reader explanations and the existing URL unless the requested architecture change calls for another location. A small correction does not require a full rewrite.

## Make the change reviewable

- Correct obsolete claims, broken references and affected steps with verified current information.
- Add a section only when it answers a relevant missing reader question.
- Retain original publication history and use a modification date that reflects the actual material update.
- Keep comparison windows and source scope with performance evidence.
- Set a follow-up from the fact's volatility or a known release/season, rather than rewriting every page on a fixed calendar.

Do not change a year or add anecdotes simply to appear fresh. If new first-party input is unavailable, use supported material and record the specific missing input in the task artifact. An interview remains optional unless the promised result requires it.

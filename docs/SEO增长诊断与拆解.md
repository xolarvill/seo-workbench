# SEO 增长诊断与拆解

SEO 经常被简化成排名问题，实际工作会继续延伸到点击、落地页、商品、询盘和成交。页面获得更多曝光后，如果点击率、产品匹配或结账体验没有改善，业务结果仍然可能不变。

本文提供一套从搜索到收入的拆解方法。它整理自一份实践笔记，并按 [SEO 基础知识与证据模型](SEO基础知识与证据模型.md) 的证据边界做了校订。这里的公式用于定位问题，不代表 Google 或任何 AI 系统公开了内部算法。

## 从问题开始，不急着解释原因

SEO 数据经常同时受到需求、品牌活动、排名、SERP 版式、页面改版、库存、价格、地区和追踪配置影响。看到流量涨跌后直接解释原因，很容易把同时发生的事情误认为因果。

先把问题写成可验证的形式：

- 变化发生在展示、点击、访问还是转化；
- 只影响品牌词还是非品牌词；
- 集中在哪类页面、设备、地区或产品；
- 是新增页面带来的总量变化，还是原有页面表现变化；
- 数据源、时间窗口和追踪口径是否一致；
- 同期是否有广告、促销、迁移、缺货或季节变化。

Workbench 负责保存网站证据，GSC 负责搜索表现，站内分析和商务系统负责访问、商品与收入。没有一个来源可以单独解释整条链路。

## 长尾、实体和信息增量

### 长尾词不是很长的词

长尾查询通常搜索量较小，需求更具体，单个词带来的流量有限，但大量长尾需求合在一起可能形成可观规模。它可以很长，也可能只是一个型号、标准或错误代码。

长尾研究更适合从任务出发：用户在选型、比较、排错、采购还是验证资质。AI 搜索让自然语言问题更常见，但“表达更长”仍不能代替意图判断。

### 实体帮助内容保持一致

实体可以理解为一个有身份、属性和关系的对象。产品、品牌、公司、人物、地点、标准和事件都可能是实体。

分析一个工业产品时，可以记录：

```text
产品
├── 型号与标识符
├── 材质、尺寸和性能
├── 适用设备与工况
├── 制造商、经销商和认证
└── 替代品、配件和维护关系
```

这种整理方式可以发现信息缺口，也能减少产品页、分类页和说明书之间的冲突。它不是关键词清单，不能通过堆放实体名称获得排名。

### 信息增量要能被证明

更有价值的内容通常包含现有结果没有充分提供的资料，例如真实测试、产品数据、选型边界、失败经验、原始图片、案例或专家解释。

“信息增量”不是要求每篇文章发明新知识。准确整理分散资料、把复杂流程讲清楚、提供更好的比较工具，也可能给用户带来实际价值。判断时要问：

- 这项信息从哪里来；
- 用户能否验证；
- 它改变了什么决定；
- 页面删除这部分后是否仍然一样有用。

## 浏览器如何得到一个页面

下面的链路用于定位网站交付和性能问题。实际顺序会受到缓存、连接复用、CDN、HTTP 版本和浏览器调度影响，并不总是逐项串行：

```text
URL
↓
浏览器缓存、Service Worker 或网络请求
↓
DNS 查询
↓
建立连接：TCP + TLS，或 HTTP/3 使用的 QUIC
↓
HTTP 请求经过 CDN、负载均衡和应用服务器
↓
返回 HTML，浏览器开始解析 DOM
↓
发现并调度 CSS、JavaScript、字体、图片等资源
↓
生成 CSSOM 与渲染树，完成样式计算和布局
↓
绘制页面，并在加载过程中产生 LCP 等测量
↓
JavaScript、事件处理和用户交互影响 INP
```

LCP 衡量最大内容元素何时完成呈现，INP 衡量用户交互的响应延迟。它们不是“页面画出来”和“页面已经可交互”的简单开关。

遇到性能问题时，把 Lighthouse 诊断、网络请求、主线程任务和 CrUX 真实用户数据分开看。技术栈名称本身不能证明瓶颈来自某个框架或插件。

## 搜索系统处理页面的链路

可以用下面的模型组织技术 SEO，但不要把它写成 Google 内部系统的完整复刻：

```text
发现 URL
↓
抓取响应
↓
必要时渲染 JavaScript
↓
理解正文、链接、媒体和页面关系
↓
选择 canonical 并判断是否索引
↓
针对具体查询生成候选结果与展示形式
↓
展示、点击和后续业务行为
```

每一层对应不同证据：

| 阶段 | 常见问题 | 主要证据 |
|---|---|---|
| 发现 | 孤立页面、导航缺口、Sitemap 缺失 | raw crawl、内部链接、Sitemap、GSC |
| 抓取 | 状态码、robots、服务器和重定向 | raw evidence、服务器日志、GSC Crawl Stats |
| 渲染 | JavaScript 外壳、移动端跳转、资源失败 | raw/rendered diff、浏览器网络证据 |
| 理解 | 页面任务不清、实体或关系混乱、模板重复 | 页面内容、结构、查询和竞品证据 |
| 索引 | canonical 冲突、重复、低价值或政策问题 | GSC URL Inspection、Sitemap、站点证据 |
| 展示 | 意图错位、SERP 功能、标题链接和摘要 | 实际 SERP、GSC 查询和页面数据 |
| 点击与转化 | 承诺不匹配、体验、价格、信任和流程 | GSC、站内分析、CRM 或电商数据 |

抓取和保存索引都需要资源，但“有抓取预算”不能解释所有未收录问题。小站通常先检查发现、状态码、canonical、重复内容和页面价值。

## AI 训练、检索和引用是三件事

模型在预训练阶段见过某个页面，不代表它会在回答中引用该页面。一个带来源的 AI 回答通常还涉及查询改写、检索候选资料、重新排序和生成，但不同产品的实现和来源政策并不相同。

```text
用户问题
↓
可能发生查询改写或工具调用
↓
检索候选网页或其他资料
↓
选择、排序和提取
↓
生成回答，可能显示来源链接
```

因此需要区分：

- 允许某个训练爬虫访问；
- 页面能否被搜索或检索系统抓取和索引；
- 页面是否真的出现在 AI 回答的来源中；
- 来源是否产生可测量的引荐访问和业务结果。

GEO 可以作为 AI 可见性和引用研究的名称，但不应脱离技术 SEO、内容质量、品牌与权威证据。当前没有一个通用公式可以计算“AI 引用概率”。

## 从展示拆到收入

电商和获客网站可以用乘法链路定位损失发生在哪一层：

```text
Organic Revenue
= Impressions
× Organic CTR
× Visit-to-Conversion Rate
× Average Order Value
```

如果已经从 session 或 click 开始计算，就不要再乘一次 CTR：

```text
Organic Revenue
= Organic Sessions
× Conversion Rate
× Average Order Value
```

复杂电商还可以继续拆：

```text
Impressions
→ Clicks
→ Landing Sessions
→ Product Views
→ Add to Cart
→ Checkout
→ Purchase
→ Repeat Purchase
```

这些是测量恒等式和业务模型，不是排名公式。每一层使用相同时间、币种、归因窗口和用户范围，数字才可以相乘。

| 现象 | 先检查 | 常见责任范围 |
|---|---|---|
| 展示下降 | 查询需求、索引页面、平均位置、品牌与非品牌 | SEO、市场需求、品牌活动 |
| 展示增长但点击不涨 | SERP 版式、查询意图、标题链接、排名分布 | SEO、内容定位 |
| 点击增长但商品浏览不涨 | 落地页任务、导航、推荐和追踪 | 内容、UX、分析 |
| 商品浏览增长但加购不涨 | 产品匹配、价格、规格、库存和信任 | 商品、定价、CRO |
| 加购增长但购买不涨 | 运费、支付、结账错误和政策 | 运营、技术、支付 |
| 首购增长但收入质量差 | AOV、退款、复购和获客成本 | 商业策略、CRM |

## 常用拆分维度

总量变化很少直接给出原因。把指标按一个维度切开，并保证其他口径尽量不变：

| 维度 | 常见分组 | 适合回答的问题 |
|---|---|---|
| 时间 | 前后周期、同比、发布前后 | 变化何时开始，是否有季节性 |
| 查询 | 品牌与非品牌，意图类型 | 增长来自品牌需求还是新增获客 |
| 位置 | 1-3、4-10、11-20、21-50 | 页面是接近突破还是整体后退 |
| 页面类型 | Product、Collection、Blog、Landing | 哪类模板贡献或损失最大 |
| 主题 | 产品、健康、比较、指南等业务主题 | 哪类内容带来有效需求 |
| 设备 | Mobile、Desktop | 是否存在移动体验或 SERP 差异 |
| 地区 | 国家、语言、市场 | 需求、库存和本地化是否匹配 |
| 用户 | New、Returning、Cohort | 变化来自获客还是留存 |
| 渠道 | SEO、Ads、Social、Email | SEO 变化是否受其他渠道影响 |
| 产品 | SKU、品类、价格带 | 流量变化还是商品变化 |
| 内容年龄 | 新页面、成熟页面、久未更新页面 | 新发布和维护策略是否有效 |

不要一次切十几个维度后挑一个看起来合理的故事。先写假设，再选能区分假设的最小拆法。

## 公司资料可以变成 SEO 资产

网站已有的运营资料往往比泛化关键词表更接近真实需求：

| 公司资料 | 可形成的公开资产 | 发布前检查 |
|---|---|---|
| 客服问题 | FAQ、帮助页、选型指南 | 去除个人信息，确认问题真实高频 |
| 售后与退货原因 | 使用教程、故障排查、产品改进 | 不掩盖产品缺陷，说明适用边界 |
| 差评 | 比较、限制说明、产品路线图输入 | 不伪造或选择性误导 |
| 好评 | 页面证据、案例、经许可的评价 | 权限、可验证性和结构化数据政策 |
| 站内搜索 | 新主题、同义词、导航改进 | 排除机器人和无结果噪声 |
| 广告搜索词 | SEO 查询和落地页假设 | 区分付费匹配逻辑与自然需求 |
| 销售和询盘 | B2B 落地页、异议处理、比较页 | 删除客户身份、报价和合同信息 |
| 用户图片 | UGC、安装案例、场景说明 | 获得使用许可并保留必要说明 |
| 邮件咨询 | 指南、比较和产品说明 | 匿名化，不公开私密业务信息 |

Schema 只能标记页面上真实可见且符合政策的内容。把好评整理成页面素材，不代表可以自动生成 `Review` 或 `AggregateRating`。

## 用 Workbench 执行一次诊断

先建立站点状态和技术基线：

```bash
./seo --project <id> evidence --rendered --technology --json
./seo --project <id> performance --json
```

Google 集成准备好后补充：

```bash
./seo --project <id> crux --json
./seo --project <id> gsc collect --json
```

对已经上线的改动，先记录假设和复查日期，再在窗口成熟后评价：

```bash
./seo --project <id> changes add --url https://example.com/page --type content \
  --hypothesis "提升合格自然点击" --metric clicks --metric conversions --json
./seo --project <id> business-signals import --from-file business-signals.csv --json
./seo --project <id> changes evaluate <change_id> --json
./seo --project <id> pages refresh --json
```

`changes evaluate` 只给出前后窗口的描述性证据，不作因果声明。`pages refresh` 合并 GSC、技术审计和线上内容 URL；某来源缺失表示 `not_observed`，不补成 0，也不能据此断言未收录或页面不存在。窗口重叠、长度不同、新内容未满 28 天或展示量不足时会要求继续观察，而不是强行给优化结论。

按下面的顺序写诊断：

1. 明确业务指标、时间窗口和变化起点。
2. 判断问题发生在发现、抓取、索引、展示、点击还是站内转化。
3. 选择一个最能区分假设的维度做拆分。
4. 把 Workbench、GSC、站内分析和商务数据放在各自能证明的范围内。
5. 写出已确认事实、推断、缺口和下一项验证。
6. 修复后用相同范围重新采集，并运行 `audit-diff` 或对应的 `changes evaluate`。

Workbench 可对已配置的 GA4 与 Shopify 项目执行只读采集，并按页面合并 sessions、key events 和商品净额；CRM 或私密客服等其他来源仍需先按页面和前后窗口聚合、匿名化，再通过 `business-signals import` 导入。不要导入用户、订单或事件标识符。完整执行格式见 [SEO 迭代闭环](SEO迭代闭环.md)。

## 诊断输出模板

```markdown
# 问题
哪个指标在什么时间、范围内发生了什么变化？

## 证据
- Workbench：站点与模板发生了什么
- GSC：查询、页面、设备和地区发生了什么
- Analytics：访问和站内行为发生了什么
- Commerce/CRM：询盘、订单、收入或质量发生了什么

## 拆分
选择了哪个维度，为什么它能区分当前假设？

## 判断
- 已确认：
- 有根据的推断：
- 仍缺少：

## 下一步
最小验证、负责人、复查窗口和成功指标。
```

这份模板的重点是让每个判断都能回到证据和业务链路，避免用一个排名、一个 Lighthouse 分数或一段流量曲线解释所有问题。
